### 1.2 Expiry mechanism: "one timer per offer" + "tick semantics" — revises Final §3 + Fig 2
- **Semantics (review fix)**: expiry is not "matching a particular message" but is **decided by server time**. Before the worker processes any command, `decide()` first sets every OFFERED offer with `expiresAt ≤ now` to EXPIRED and releases its seat ("tick-first"), then executes the command itself. Hence: late/duplicate/stale timer messages are all **harmless no-ops**; an ACCEPT after `expiresAt` is rejected even if the timer has not arrived yet; C5 thereby holds in a stronger form (the report is reworded to: expiry is decided by server time at the moment of processing, and a late tick cannot invalidate a newer offer that has not yet expired).
- **Main path (determines the latency)**: for each new offer the worker sends one `TICK{workshopId, offerId, expiresAt}` to the **standard SQS queue `expiry-delay`**, `DelaySeconds = clamp(expiresAt − now, 0, 900)`; when the delay is up, the `expiryForwarder` Lambda puts `TICK{workshopId}` onto **the same FIFO queue, with the same MessageGroupId = workshopId** (dedup id `tick#offerId#expiresAt`), and the worker processing a TICK = one run of tick-first + allocate. The timer message is sent **before the transaction commits** (an extra tick is harmless), so the hardest path to test, "send fails after commit→redelivery→resend on replay", is no longer needed.
- **Key facts (go into the report; checked against the AWS documentation)**: the SQS documentation states "FIFO queues don't support timers on individual messages", and the message timer maximum is 15 min; so the timer goes on a standard queue and is then moved into the FIFO, keeping "releases and new requests share one ordered path per workshop". The alternative, EventBridge Scheduler (one-time `at()`, no 15 min limit, recommended by AWS for longer delays), is listed in the report as "considered": this project's hold ≤ 15 min falls within the SQS limit, and there is no need to add one more service and a PassRole permission.
- **Safety net (not on the latency path)**: the workshop META maintains `nextDueAt = min(earliest live offer expiresAt, nearest session cutoffAt)` and writes it into a sparse GSI (`GSI1PK='DUE'`, `GSI1SK=nextDueAt#wsId`); EventBridge triggers `sweep` every 5 min, which queries the workshops with `nextDueAt ≤ now` and enqueues a TICK. It also honours R4's cut-off (once it is reached, that session allocates no more; if every acceptable session of a registration is past its cut-off → ENDED(CUTOFF)) and "recovery within 5 min after a failure". In normal operation the ticks enqueued by the sweep should cause no expiry at all; the metric `SweepLateExpiries` should be 0. The report states: **the sweep interval no longer constrains the backfill latency**.
- **Hold duration configurable per workshop** (review fix): `holdSeconds` default 900, minimum 30; experiments use 60 s so that each sample does not wait 15 min; the report states the default and the experimental setting.
- **Latency budget (the report gives a table)**: SQS delay precision (whole seconds) + forwarder invocation + FIFO enqueue + worker transaction ≈ an expected p95 in single-digit seconds; a backfill caused by a cancellation/decline happens **inside the same transaction**, latency ≈ 0, reported separately. 120 s remains the acceptance ceiling; the actual value is given from measurement.

### 1.3 202 settlement: **Polling protocol** (written explicitly into Final §3 + Fig 2 step 9)
- `commandId` is **generated by the client** (UUID v4, saved with the form, reused on retry). `POST /workshops/{id}/commands` → the API conditionally writes `CommandResult{status: ACCEPTED, acceptedAt}` (`attribute_not_exists(PK)` + `ReturnValuesOnConditionCheckFailure: ALL_OLD`: if it already exists, the existing result is returned directly with no second read → repeat submissions are idempotent, C3) → enqueue on the FIFO (on failure, conditionally delete that CMD and return 503, so the browser never polls an orphan) → return **202** `{commandId, status:"ACCEPTED", href:"/commands/{id}", pollAfterMs:300}`.
- The browser polls `GET /commands/{id}` (DynamoDB **ConsistentRead**) with backoff 300 → 500 → 1000 → 2000 ms (capped); after a 30 s budget it drops to background polling every 5 s and shows "still processing". Terminal states `APPLIED{result}` / `REJECTED{reason}`; `result` carries the registration status and an offer summary, so the UI can update from the poll response alone (avoiding the staleness risk of reading the GSI right after settlement).
- The participant status page refreshes every 10 s while a QUEUED/OFFERED registration exists (paused while the page is not visible), to receive changes **not triggered by the participant themselves** (getting an offer through a backfill).
- The UI must distinguish "request received" from "seat confirmed" (a report commitment): toast "Received, processing…" → after settlement "A seat in Session 2 is held for you, confirm within 14:59" / "Queued, position 3" / "Rejected: reason".
- The report states **why there is no WebSocket**: no benefit at pilot scale, and it adds one more kind of API, a connection table and a failure point; performance metrics report "server-side settle latency" (settledAt − acceptedAt, written on the CMD) and "client-observed latency" (including the polling quantisation error, at most +2 s) separately; k6 polls at a fixed 200 ms only to detect completion.

### 2.2 Domain model and commands (packages/core)
- **Entities**: `Organization{id, name, ownerUserId, members[]}`; `Workshop{id, orgId, title, description, status: OPEN|CLOSED|CANCELLED, mode: UNIFIED|PER_SESSION, holdSeconds, seq, version, nextDueAt}`; `Session{id, workshopId, title, startsAt, cutoffAt(=startsAt−30 min), capacity, confirmed, held, status: OPEN|CANCELLED}`; `Registration{workshopId, userId, seq, acceptable: sessionId[](preference order), status: QUEUED|OFFERED|CONFIRMED|CANCELLED|ENDED, endReason?, currentOfferId?, confirmedSessionId?}`; `Offer{id, workshopId, sessionId, userId, status: OFFERED|ACCEPTED|DECLINED|EXPIRED|REVOKED, createdAt, expiresAt}`; `CommandResult{commandId, type, actorUserId, workshopId, status: ACCEPTED|APPLIED|REJECTED, reason?, result?, acceptedAt, settledAt, ttl}`; `Notification{id, userId, kind, offerId?, body, status: PENDING|SENT|FAILED|SKIPPED, attempts, ttl}`; `BackfillRecord{workshopId, sessionId, releasedAt, cause: EXPIRED|DECLINED|CANCELLED_CONFIRMED|CANCELLED_OFFER|CAPACITY_UP, reallocatedAt?, newOfferId?, latencyMs?}`; `Attendance{workshopId, userId, attended, markedAt}` (written synchronously by the API, not under the worker lock).
- **Commands** (all carry the client's `commandId`, `actorUserId`(from the JWT, not in the body), `workshopId`): participant `REGISTER{acceptable[]}`, `ACCEPT_OFFER{offerId}`, `DECLINE_OFFER{offerId}`, `CANCEL_REGISTRATION`; organiser `SET_CAPACITY{sessionId, capacity}`, `CANCEL_SESSION{sessionId}`, `CANCEL_WORKSHOP`, `CLOSE_REGISTRATION`/`OPEN_REGISTRATION`; internal `TICK` (no CMD record, idempotent by nature), `REALLOCATE` (continuation). Creating a workshop/session, editing the title and attendance marking are **synchronous REST**. Every operation that changes state in the `WS#` partition goes through a command (the worker is the only writer, which is the precondition for the single META lock).
- **Pure function** `decide(snapshot, command, now): Decision` → `{status, reason?, writes: Change[], notifications[], timers: {offerId, expiresAt}[], backfills[]}`. Steps: (1) tick-first: expire every due offer, handle sessions past their cut-off; (2) apply the command; (3) `allocate()`: scan QUEUED registrations by seq and, in preference order, find the first session with `free = capacity − confirmed − held > 0` and `now < cutoffAt` → Offer (`expiresAt = min(now + holdSeconds, cutoffAt)`), `held++`, Registration→OFFERED, Notification, fill in `reallocatedAt` on the BackfillRecord; (4) recompute `nextDueAt`. Each command creates at most **12** offers; beyond that it produces a `REALLOCATE` continuation (the 100-item transaction limit).
- **Where the rules are enforced**: R1 = conditional write of the uniqueness marker item `L#U#{userId}`; R2 = `seq` incremented by the single-writer worker; R3 = allocate's in-order scan; R4 = expiresAt/cutoffAt + sweep tick; R5 = DECLINE/EXPIRE removes that session from acceptable, ENDED if none is left, otherwise back to QUEUED and allocate again immediately; R6 = CANCEL leaves entirely, re-registering gets a new seq; R7 = SET_CAPACITY rejects `capacity < confirmed + held`, and a capacity increase allocates immediately; CANCEL_SESSION turns that session's OFFERED→REVOKED and CONFIRMED→back to QUEUED (the session is removed from the acceptable set) and notifies.
- `checkInvariants(snapshot)`: C1 `confirmed + held ≤ capacity`, `held == that session's OFFERED count`; C2 each account has ≤ 1 OFFERED/CONFIRMED per workshop; "no starvation": there is no QUEUED registration with an acceptable session that still has a free seat and is not past its cut-off. Used by the tests, the experiments and the `verify` endpoint.
- `mode: PER_SESSION` strategy: a registration is bound to a single session, every session has its own queue, no cross-session constraint is applied; the report states "baseline = same engine + per-session allocator, replayed under a simulated clock".
- Tests: vitest covers every rule and every reject reason; after fast-check random command sequences (≥ 2,000 sequences, length ≤ 200, including random clock advances) `checkInvariants` must pass; coverage target core ≥ 95% branches.

### 2.3 DynamoDB key design and transactions (services/aws/src/adapters/dynamo)
Single table `seatrelay-{stage}`, PK/SK strings, On-demand, PITR on (DeletionProtection off in dev), Streams `NEW_AND_OLD_IMAGES`, TTL attribute `ttl` (epoch seconds). **Separate live / history prefixes** (review fix: keeps the snapshot Query from slowing down as experiments accumulate):
| Item | PK | SK | Notes |
|---|---|---|---|
| Organization | `ORG#{orgId}` | `META` | members; GSI1 `U#{userId}`→`ORG#` to look up my organisations |
| Workshop | `WS#{wsId}` | `L#META` | seq/version/holdSeconds/nextDueAt; GSI1PK `ORG#{orgId}` GSI1SK `WS#{createdAt}`; sparse `GSI1PK='DUE'` only while OPEN and something is due |
| Session | `WS#{wsId}` | `L#S#{sessionId}` | capacity/confirmed/held/cutoffAt |
| Live Registration | `WS#{wsId}` | `L#R#{seq:08d}` | QUEUED/OFFERED/CONFIRMED; GSI1PK `U#{userId}` GSI1SK `WS#{wsId}` to look up my registrations |
| Uniqueness marker | `WS#{wsId}` | `L#U#{userId}` | {seq,status}; R1/C2; O(1) consistent read |
| Live Offer | `WS#{wsId}` | `L#O#{offerId}` | OFFERED only |
| History Registration/Offer | `WS#{wsId}` | `H#R#{seq}` / `H#O#{offerId}` | on settlement, Delete live + Put history (same transaction) |
| BackfillRecord | `WS#{wsId}` | `H#BF#{releasedAt}#{id}` | dashboard + backfill latency |
| Attendance | `WS#{wsId}` | `H#A#{userId}` | synchronous API write |
| CommandResult | `CMD#{commandId}` | `META` | ttl 30 days; includes acceptedAt/settledAt/result |
| Notification | `U#{userId}` | `N#{createdAt}#{id}` | entityType=NOTIFICATION; ttl 90 days |
- worker snapshot = `Query PK=WS#{wsId} AND begins_with(SK,'L#')` (ConsistentRead) — reads only live items; its size is bounded by capacity + queue length.
- **Commit (review fix)** = one `TransactWriteItems`: conditions go only on **the items being written**: `L#META` carries `version = :snapshot` (+1 per transaction; it is the optimistic lock of the whole workshop, and its precondition = the worker is the only writer of `WS#`); the `CMD#` update carries `status = ACCEPTED`; new items `attribute_not_exists`. **No** ConditionCheck on unchanged items (the 100-item limit, and a Put+ConditionCheck on the same key raises ValidationException). `TransactionCanceledException` branches on `CancellationReasons[i].Code`: CMD failed → already settled, ack (redelivery is idempotent, C3); META failed → reload the snapshot in-process and retry ≤ 3 times; anything else → throw.
- Timers are sent before the commit (`SendMessageBatch` to `expiry-delay`); an extra tick is harmless.

### 2.7 On-premise reference (services/local, for the cost comparison and for verifying equivalent functionality)
- `docker-compose.yml`: `postgres:16-alpine`, `keycloak:26` (`start-dev --import-realm`; the realm contains the public PKCE client `seatrelay-web`, a `tooling` client with the password grant enabled, test users), `axllent/mailpit`, `server` (Node 20: Fastify API + in-process worker/timer/notifier loops), `web` (nginx serves the same SPA build, `env.js` injects issuer/API).
- Postgres schema: organizations, workshops, sessions, registrations, offers, command_results, notifications, backfill_records, attendance, **commands** (queue: id, workshop_id, payload, status, available_at, attempts), **timers** (workshop_id, fire_at).
- worker: every 200 ms `SELECT … FROM commands WHERE status='PENDING' AND available_at<=now() ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1` + `pg_advisory_xact_lock(hashtext(workshop_id))` to serialise each workshop → the same `decide()` (with tick-first) → apply the writes in a single transaction → insert timers. The timer loop turns due timers into TICK commands every 1 s; the notifier loop sends over SMTP to Mailpit.
- Keycloak issuer pitfall: the browser uses `http://localhost:8080/realms/seatrelay`; the server checks `iss` against the same string and fetches the JWKS from the in-container address (`KC_HOSTNAME=http://localhost:8080`).
- Fallback if Docker cannot be installed (Windows Home needs WSL2): Postgres installer + Keycloak zip (JDK 21) + e-mail written to the log; failing that, run the one-click script on a team member's Mac/Linux.
- Measurement: the same k6 scripts; `docker stats` sampling → CPU/RAM curves → on-prem hardware specification and cost model.

### 2.8 Observability, security
- Structured JSON logs with commandId/workshopId; X-Ray tracing API→SQS→worker→DDB (can be cut); EMF custom metrics (low-cardinality dimensions).
- Security: JWT validation, organisation ownership check (C7), zod input validation, throttling, CORS, least-privilege IAM, no secrets in the SPA, PII limited to e-mail address + display name, TTL retention periods; `npm audit` in CI. Credentials are written into `%USERPROFILE%\.aws\credentials` on this machine only by a team member, never through me.

## 4. System experiment plan (Table 3 item by item → method → output)
| Table 3 item | Method (script) | Pass criterion / what is reported |
|---|---|---|
| Core correctness | `correctness.ts`: scripted scenarios (register/confirm/decline/cancel/change capacity/cancel session/cancel event) run on dev, `verify` after every step | 0 over-capacity, 0 double holds; list the result of every scenario |
| Preference, order | core property tests (2,000 random sequences) + replay of 20 fixed cases on dev | never allocates an unacceptable session; preference order correct |
| Concurrency | `concurrency.ts`: 50 accounts concurrently compete for 3 sessions with 5 seats in total; the same account sends accept/decline/cancel concurrently | final state satisfies every invariant; record the number of META conflict retries (expected 0, because of the single FIFO consumer) |
| Repeat execution | the same commandId submitted 5 times concurrently; `_fault: AFTER_COMMIT` simulates a crash after commit to trigger redelivery | no double decrement/double release; CMD unique and APPLIED once |
| Expiry race | holdSeconds=60: send one ACCEPT at expiresAt − 200 ms and one at + 200 ms; manually put a late TICK on the FIFO | the former succeeds, the latter REJECTED(expired), regardless of whether the timer has arrived; a late tick does not affect a newer offer |
| Failure recovery | `_fault: BEFORE_COMMIT`/`AFTER_COMMIT`/`TIMER_SEND`; set the notifier's reserved concurrency to 0 → record the backlog → restore → Streams retries deliver | recoverable, traceable (logs/X-Ray); recovery < 5 min (record the actual seconds) |
| Access control | negative cases: confirming someone else's offer, cross-organisation dashboard/export/capacity change, no token, reading someone else's CMD | 401/403/404 all correct |
| Performance | k6 10/25/50 VUs × 2 scenarios × 3 rounds | read and 202 p95 < 1 s; settle p95 < 5 s (server-side and client-side measures kept separate); error rate; queue depth; if hot-spot misses the target, report it truthfully and explain single-workshop serialisation |
| Backfill latency | `backfill.ts`: holdSeconds=60, 100 offers left to expire with people waiting further back in the queue; latency = reallocatedAt − expiresAt; cancellation-driven backfills counted separately | p95 ≤ 120 s (single-digit seconds expected); outliers listed; `SweepLateExpiries` (expected 0) |
| Cost | usage × unit price + Cost Explorer daily; local reference under the same load | unit cost and its trend with scale; three layers |
| Mechanism comparison | `tools/replay` (1,000 seeds, simulated clock) + one real replay of each mode on dev | comparison charts of duplicate holds, distinct served, backfill time |

## 9. Risks and fallbacks
- **SES sandbox**: production not approved → pilot e-mails go only to the team's verified addresses, participants rely on in-app notifications (the report says so truthfully); Cognito 50 e-mails/day → pre-create accounts + spread sign-ups over several days.
- **Docker Desktop cannot be installed** → Podman/Rancher Desktop; failing that, the no-Docker fallback of §2.7 or run it on a team member's Mac/Linux.
- **Cost overrun**: Budget (credits excluded) alerts + throttling + MaximumConcurrency + daily snapshots + teardown after the experiments; load capped at 50 VUs.
- **Hot-spot performance misses the target**: first apply 1024 MB arm64 + live snapshot + the BatchSize 10 shared-snapshot optimisation; if it still misses, report it truthfully and explain that serialisation is a design property.
- **SAM on Windows**: avoided with our own esbuild output; if `sam deploy` still has problems, use `aws cloudformation package/deploy`.
- **Recruitment falls short**: start two weeks early; report the actual sample, do not make up data.
- **Cut order if time runs short**: Keycloak (switch to a local development token issuer and declare it) → Mailpit (e-mail written to the log) → X-Ray and EMF (use built-in metrics + Logs Insights) → secondary dashboard charts (keep the alarms) → REALLOCATE continuation (cap 20 offers/transaction, completed by the sweep) → organisation member invitations → local reference runs only 10/25 VUs → mechanism comparison by simulation only, no replay on the real system. **Not cut**: core tests, idempotency, timers+sweep, access control, k6, cost records, CSV export, user study, report and demo.
