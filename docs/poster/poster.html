SeatRelay

One waitlist for every session of a workshop.

Register once and rank the sessions you can attend. A freed seat is held for the next person in line who can attend that session, not left empty or waiting for an organiser’s e-mail.

Why one form per session ties up seats

Simulated on 1,000 random workshops: the same arrivals replayed through both designs

A simulation, not field data: our allocation engine with assumed behaviour; means per workshop, refill time (incl. people’s replies) as the median workshop (means 15.7 vs 4.3 min). The baseline’s waitlists are automatic too, so the gap comes only from people holding several seats.

How it works

  1. Tick every session you could attend and rank them.
  2. Wait in one queue. When a seat you can take frees up and you are first, it is held for you (15 min by default).

    Staged run with test accounts and 1-minute holds.

  3. Accept to keep it. Decline or let it lapse: you lose only that session, and the seat moves on at once.
  4. Organisers see every hand-over and its delay.

    Top row: an offer expired; the seat was re-held 189 ms later.

Serverless on AWS

  • Each workshop’s requests are decided in arrival order; a version check catches any overlap.
  • Seats, queue, offer and notice change in one transaction.
  • Each hold has its own timer, and a late timer cannot touch a newer offer.

Cost model, list prices: US$13.30 per 1,000 registrations at 1k a month, US$5.91 at 100k. An own server is cheaper above about 57,000 a month if fully costed, or about 3,900 if one is already running.
