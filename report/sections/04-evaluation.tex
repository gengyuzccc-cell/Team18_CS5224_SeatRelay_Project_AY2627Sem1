\section{Evaluation}\label{sec:evaluation}

\subsection{Method}
Commands went through the \code{dev} stage's public API as the browser sends them (client
\code{commandId}, POST, 202, polling as in \S\ref{sec:timers}). Crashes were injected with
\code{\_fault} flags that only \code{dev} honours, stale TICKs were sent directly to the FIFO queue,
and the notifier outage was simulated by setting its reserved concurrency to 0; \code{dev} records
notifications as SKIPPED without sending e-mail. Each script asserts its checks, calls \code{verify}
after its scenario steps and writes \code{results/<date>-<experiment>/}; each experiment ran 3 times,
and the latest complete run is quoted. Expiry experiments use $\text{holdSeconds} = 60$. The smoke
test passed first (\SmokeChecksPassed/\SmokeChecksTotal{} checks, run \code{\SmokeRunId}). The
\SeriesExperiments{} quoted runs recorded \SeriesCommitCount{} commits (\code{\SeriesCommits});
\SeriesDirtyRuns{} runs had uncommitted changes in the working tree: \pending{confirm that the dev
Lambda code was not redeployed between these commits and that only results/ and docs/ were
uncommitted, or re-run from a clean checkout}. Run ids and commits of every number are listed in
\code{report/generated/numbers.tex}.

\paragraph{Failed checks.}
In their latest runs \SeriesFailed{} of the \SeriesExperiments{} experiments failed a check
(\SeriesFailedNames), and we report them as failures. In the \emph{concurrency} run,
\ConcurrencyTransportErrors{} of \ConcurrencyCommands{} requests received HTTP 503 responses without
an application error code, so not from the API's own 503 path (failed enqueue); some of these
commands were nevertheless applied, so the harness's expected sequence numbers and confirmation
counts no longer matched, although \code{verify} found no invariant violation after any phase. The
version-conflict metric read \ConcurrencyMetaRetries, but CloudWatch returned no SeatRelay samples
in that window, so that reading is inconclusive. The \emph{backfill} run aborted at its first request
(creating a workshop) with the same kind of 503 and produced no latency samples. The pilot stack was
deployed during the concurrency run window, a possible confounder for the re-run to exclude, and the
account's Lambda concurrency quota is 10, shared by both stages' functions (an increase is pending).
\pending{root cause of the HTTP 503 responses, then clean concurrency and backfill re-runs}. An
earlier \emph{expiry-race} run failed one check: a probe meant to arrive 200\,ms before
\code{expiresAt} arrived after it (client send-timing jitter) and was rejected as expired, as the
server clock requires; the harness now calibrates the send time, and the quoted run
(\code{\ExpiryRaceRunId}) is a re-run. In all \ExpiryRaceOrderTimerFirst{} late trials the timer had
expired the offer before the ACCEPT arrived, so the opposite order was not observed on \code{dev};
the engine's unit tests cover it. No stale tick changed a newer offer.

\paragraph{Latency.}
In the correctness run the server settled commands with p95 \CorrectnessSettleServerPNinetyFiveMs\,ms
(\CorrectnessSettleClientN{} commands) and the client observed p95
\CorrectnessSettleClientPNinetyFiveMs\,ms, which adds the first 300\,ms poll interval, the round
trips and up to one further interval. In the concurrency run, where one workshop's commands are
serialised by design, the server p95 rose to \ConcurrencySettleServerPNinetyFiveMs\,ms, above the
5\,s target (with the 503 responses above). After a worker crash, the 120\,s visibility timeout bounds
the recovery of a stalled workshop (Table~\ref{tab:results}).

\subsection{Mechanism comparison: one queue vs per-session forms}\label{sec:mechanism}
The replay tool runs the production engine with a simulated clock and ideal timers on
\ReplaySeeds{} random workshops (\ReplayRangeSessionsMin--\ReplayRangeSessionsMax{} sessions,
\ReplayRangeOversubscriptionMin--\ReplayRangeOversubscriptionMax{} times oversubscribed, holds of
\ReplayRangeHoldSecondsMin--\ReplayRangeHoldSecondsMax\,s, random accept, decline, ignore, cancel and
hoarding behaviour). Each seed's identical arrival stream is replayed twice: in UNIFIED mode (SeatRelay) and in
PER\_SESSION mode, where a participant registers separately for every acceptable session, each
session has its own queue, and duplicates are released by hand only with some probability. One queue had
no duplicate holds, as C2 requires; per-session queues had
\ReplayDupHoldEventsPerSessionMean{} duplicate-hold events per workshop
[\ReplayDupHoldEventsPerSessionLo, \ReplayDupHoldEventsPerSessionHi] (Fig.~\ref{fig:replay}). One
queue served \ReplayDistinctUnifiedMean{} distinct participants per workshop against
\ReplayDistinctPerSessionMean{} (paired difference \ReplayDistinctDeltaMean{}
[\ReplayDistinctDeltaLo, \ReplayDistinctDeltaHi]; fewer under PER\_SESSION in
\ReplayDistinctFewerSeedsPct\,\% of seeds, equal in \ReplayDistinctEqualSeedsPct\,\%), and a released
seat reached a new participant after \ReplayRefillMeanUnifiedMean{} instead of
\ReplayRefillMeanPerSessionMean{} minutes on average (\ReplayRefillMeanN{} seeds with refills in both
modes). Seats left empty at cut-off did not differ (difference \ReplaySeatsWastedDeltaMean{}
[\ReplaySeatsWastedDeltaLo, \ReplaySeatsWastedDeltaHi]). This compares two modes of our own engine
under an assumed behaviour model: it is neither a field measurement nor a test of the tools in
Table~\ref{tab:competitors}; the plan's extra replay on the deployed system was not carried out.

\subsection{User study}\label{sec:study}
Twelve people outside the team (at least four with organising experience) use SeatRelay and a
control that mirrors current practice, one Google Form per session plus a shared Sheet with
duplicate-detection formulas, in counterbalanced order with equivalent data sets; a two-person pilot
run precedes them and is excluded, and if recruitment falls short we report the real sample and its
limits. Participants perform five tasks (choose acceptable sessions, join the waitlist, interpret
their status, confirm, cancel) and organisers four (create a multi-session workshop, handle a
cancellation, inspect the backfill, read the distinct count and export). We measure completion,
paired task time (Wilcoxon signed-rank test~\cite{wilcoxon1945}), the original ten-item
SUS~\cite{brooke1996sus}, erroneous actions, help requests and the organiser's manual steps.

\subsection{Real pilot}\label{sec:pilot}
The \code{pilot} stage (fault injection disabled, e-mail enabled; while SES is in the sandbox only
verified addresses receive mail and others rely on in-app notifications) is deployed to serve a real
workshop in two sessions with registration open for at least five days; the organiser's CSV exports
and the dashboard's backfill log will be the evidence. \pending{pilot workshop, dates and
observations: natural cancellations, backfills, notifications, attendance, organiser feedback}.

\subsection{Hypotheses H1--H3: verdicts on the evidence so far}\label{sec:hypotheses}
\begin{itemize}
\item \textbf{H2} (the cross-session constraint removes the capacity waste of duplicate holds):
  \emph{supported in simulation, not yet in the field.} One queue had no duplicate holds against
  \ReplayDupHoldEventsPerSessionMean{} duplicate-hold events per workshop with per-session queues and
  served \ReplayDistinctUnifiedMean{} instead of \ReplayDistinctPerSessionMean{} distinct participants
  (\S\ref{sec:mechanism}); seats left empty at cut-off did not differ, so the waste removed is
  capacity tied up by duplicates, not seats empty at the end. No \code{verify} call on \code{dev}
  found a C2 violation.
\item \textbf{H3} (automatic backfill reduces the organiser's manual handling): \emph{partly
  supported.} Every release is relayed in the same decision with no organiser step
  (\TimerPathRelaysN{} timer-path relays took at most \TimerPathRelayMaxMs\,ms; a cancellation is
  relayed inside its own transaction, \SmokeCancelBackfillMs\,ms), and in simulation per-session forms left
  \ReplayDupConfirmedPerSessionMean{} duplicate confirmed seats per workshop to clean up, against
  \ReplayDupConfirmedUnifiedMean{} with one queue. Open: \IfPending{\BackfillExpiredPNinetyFiveS}{the
  backfill-latency target (run aborted, \S\ref{sec:results}) and }{}\IfPending{\StudyParticipants}{the
  organiser's manual steps in the user study (\S\ref{sec:study}).}{\pending{H3: compare the organiser's
  manual steps in the user study}}
\item \textbf{H1} (unified registration reduces participant effort): \IfPending{\StudyParticipants}{\emph{not
  tested yet}; it rests on the user study's paired task times, completion, errors and help requests
  (\S\ref{sec:study}).}{\pending{H1 verdict from the user-study results (\S\ref{sec:study})}}
\end{itemize}
