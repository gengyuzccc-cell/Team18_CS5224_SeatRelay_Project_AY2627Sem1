\section{Evaluation}\label{sec:evaluation}

\subsection{Method}
Commands went through the \code{dev} stage's public API as the browser sends them: client
\code{commandId}, POST, 202, then polling with the back-off of \S\ref{sec:timers}. Crashes were
injected with \code{\_fault} flags that only \code{dev} honours, stale TICKs were sent directly to
the FIFO queue, and the notifier outage was simulated by setting its reserved concurrency to 0. On
\code{dev} e-mail is disabled, so the notifier records each notification as SKIPPED without sending
it. Each script asserts its checks, calls \code{verify} after its scenario steps and writes
\code{results/<date>-<experiment>/}; each experiment ran 3 times in one invocation, and the latest
complete run is quoted. Expiry experiments use $\text{holdSeconds} = 60$ so that a sample does not
take 15 minutes. The acceptance smoke test passed before the series
(\SmokeChecksPassed/\SmokeChecksTotal{} checks, run \code{\SmokeRunId}). The \SeriesExperiments{}
quoted runs recorded \SeriesCommitCount{} commits (\code{\SeriesCommits}); \SeriesDirtyRuns{} runs had
uncommitted changes in the working tree: \pending{confirm that the dev Lambda code was not redeployed between
these commits and that only results/ and docs/ were uncommitted, or re-run from a clean checkout}.
Run ids and commits of every number are listed in \code{report/generated/numbers.tex}.

\paragraph{Failed checks.}
In their latest runs \SeriesFailed{} of the \SeriesExperiments{} experiments failed a check
(\SeriesFailedNames), and we report them as failures. In the \emph{concurrency} run,
\ConcurrencyTransportErrors{} of \ConcurrencyCommands{} requests received HTTP 503 responses without
an application error code, so they did not come from the API's own 503 path (failed enqueue).
Because some of these commands were nevertheless applied, the harness's expected sequence numbers
and confirmation counts no longer matched, although \code{verify} found no invariant violation after
any phase. The version-conflict metric read \ConcurrencyMetaRetries, but CloudWatch returned no
samples for any SeatRelay metric in that window, so that reading is inconclusive. The
\emph{backfill} run aborted at its first request, creating a workshop, with the same kind of 503,
so it produced no latency samples. The pilot stack was deployed to the same account around the time
of the concurrency run (its deployment record falls inside the run window), a possible confounder
for the re-run to exclude. \pending{root cause of the HTTP 503 responses, then clean
concurrency and backfill re-runs}. An earlier \emph{expiry-race} run failed one check because a probe
meant to reach the API 200\,ms before \code{expiresAt} arrived after it (client send-timing jitter)
and was rejected as expired, which agrees with the server clock; the harness now calibrates the
send time, and the quoted run (\code{\ExpiryRaceRunId}) is a re-run.
In all \ExpiryRaceOrderTimerFirst{} late trials the timer's tick had expired the offer before the
ACCEPT arrived, so the opposite order (ACCEPT before the timer) was not observed on \code{dev}; the
engine's unit tests cover it. No stale tick changed a newer offer.

\paragraph{Latency.}
In the correctness run the server settled commands with p95 \CorrectnessSettleServerPNinetyFiveMs\,ms
(\CorrectnessSettleClientN{} commands); the client observed p95 \CorrectnessSettleClientPNinetyFiveMs\,ms,
because it adds the first 300\,ms poll interval, the request round trips and up to one further
interval. In the concurrency run, where all commands of one workshop are serialised in one FIFO
group by design, the server p95 rose to \ConcurrencySettleServerPNinetyFiveMs\,ms, above the 5\,s
settle target (the same run had the 503 responses above). After a worker crash a command settles when
the 120\,s visibility timeout returns the message (median \FailureBeforeCommitSettleMedianS\,s), which
bounds the recovery of a stalled workshop.

\subsection{Mechanism comparison: one queue vs per-session forms}\label{sec:mechanism}
The replay tool runs the production engine with a simulated clock and ideal timers on
\ReplaySeeds{} random workshops (\ReplayRangeSessionsMin--\ReplayRangeSessionsMax{} sessions,
\ReplayRangeOversubscriptionMin--\ReplayRangeOversubscriptionMax{} times oversubscribed, holds of
\ReplayRangeHoldSecondsMin--\ReplayRangeHoldSecondsMax\,s, random accept, decline, ignore, cancel and
hoarding behaviour). Each seed's identical arrival stream is replayed twice: in UNIFIED mode (SeatRelay) and in
PER\_SESSION mode, where a participant registers separately for every acceptable session, each
session has its own queue, and duplicates are released by hand only with some probability. With one
queue there were no duplicate holds, as C2 requires; with per-session queues there were
\ReplayDupHoldEventsPerSessionMean{} duplicate-hold events per workshop
[\ReplayDupHoldEventsPerSessionLo, \ReplayDupHoldEventsPerSessionHi] (Fig.~\ref{fig:replay}). One
queue served \ReplayDistinctUnifiedMean{} distinct participants per workshop against
\ReplayDistinctPerSessionMean{} (paired difference \ReplayDistinctDeltaMean{}
[\ReplayDistinctDeltaLo, \ReplayDistinctDeltaHi]; fewer under PER\_SESSION in
\ReplayDistinctFewerSeedsPct\,\% of seeds, equal in \ReplayDistinctEqualSeedsPct\,\%), and a released
seat reached a new participant after \ReplayRefillMeanUnifiedMean{} instead of
\ReplayRefillMeanPerSessionMean{} minutes on average (\ReplayRefillMeanN{} seeds with refills in both
modes). Seats left empty at cut-off did not differ (difference \ReplaySeatsWastedDeltaMean{}
[\ReplaySeatsWastedDeltaLo, \ReplaySeatsWastedDeltaHi]). The comparison is a simulation with an
assumed behaviour model, not a field measurement; the plan's additional replay on the deployed system
was not carried out.

\subsection{User study}\label{sec:study}
The protocol has twelve people outside the team (at least four with organising experience) use
SeatRelay and a control that mirrors current practice, one Google Form per session plus a shared Sheet with
duplicate-detection formulas, in counterbalanced order with equivalent data sets. Participants
perform five tasks (choose acceptable sessions, join the waitlist, interpret their status, confirm,
cancel) and organisers four (create a multi-session workshop, handle a cancellation, inspect the
backfill, read the distinct count and export). We measure completion, paired task time (Wilcoxon
signed-rank test~\cite{wilcoxon1945}), SUS~\cite{brooke1996sus}, erroneous actions, help requests and
the organiser's manual steps.

\subsection{Real pilot}\label{sec:pilot}
The \code{pilot} stage (fault injection disabled, e-mail enabled; while SES is in the sandbox only
verified addresses receive mail and others rely on in-app notifications) is deployed to serve a real
workshop in two sessions with registration open for at least five days; the organiser's CSV exports
and the dashboard's backfill log will be the evidence. \pending{pilot workshop, dates and
observations: natural cancellations, backfills, notifications, attendance, organiser feedback}.
