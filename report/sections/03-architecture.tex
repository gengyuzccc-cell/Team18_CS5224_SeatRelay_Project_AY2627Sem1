\subsection{Components and layering}
SeatRelay runs in one AWS region (\code{ap-southeast-1}) from three CloudFormation templates:
identity (Cognito user pool, Simple Email Service (SES) identity, budgets; deployed once),
application, and web (private S3 bucket behind CloudFront with origin access
control~\cite{aws-cloudfront-oac}), the last two once per stage: \code{dev} for experiments,
\code{pilot} for real users. Users sign in on the Cognito hosted page (authorization code flow with
PKCE), and the HTTP API validates the JSON Web Token's (JWT) signature, issuer and audience before
any authenticated route~\cite{aws-apigw-jwt}. Five Lambda functions (arm64, Node.js~22, X-Ray) do the
work (Fig.~\ref{fig:arch}); two Simple Queue Service (SQS) queues, a first-in-first-out (FIFO)
command queue and a standard delay queue, carry commands and timers; state lives in one DynamoDB
table (on-demand, point-in-time recovery (PITR), Streams, time-to-live (TTL)). Pay-per-request
services suit bursty, mostly idle registration traffic: they span AZs with no servers to patch, and
idle cost is close to zero after the free allowances (\S\ref{sec:business}). All business rules are
in a pure engine, \code{decide(snapshot, command, now)} in \code{packages/core}, which returns the
writes, notifications, timers and backfill records of one decision without I/O; adapters map them
to DynamoDB or PostgreSQL, so one engine runs in the cloud, on-prem and in the replay simulator
(\S\ref{sec:mechanism}).

\subsection{Write path, data model and the single-writer lock}\label{sec:writepath}
Reads are served directly; set-up, title edits and attendance are synchronous writes outside the
fields the engine owns.
Every change to seats, queues or offers is a \emph{command} with a client-generated
\code{commandId}. The API writes \code{CMD\#\{commandId\}} = ACCEPTED (conditional on absence; a
repeat returns the existing record), enqueues the command on the FIFO queue with message group =
workshop and deduplication id = \code{commandId}~\cite{aws-sqs-exactly-once}, and answers 202; if the
enqueue fails, it deletes the record and answers 503, so no browser polls an orphan. SQS FIFO
delivers a group's messages one at a time and in
order~\cite{aws-sqs-fifo,aws-sqs-fifo-terms,aws-lambda-sqs-scaling}, so each workshop has one serial
writer while workshops are processed in parallel (worker concurrency 5).

A workshop lives in one partition \code{WS\#\{id\}}: the \emph{live} items a decision needs under
\code{L\#} (META item, sessions, live registrations and offers, pending backfills, a due-date marker)
and settled \emph{history} under \code{H\#}. The worker reads only \code{L\#} with a strongly
consistent query, so its snapshot is bounded by capacity and queue length, not by age.
\code{decide()} expires what is due (\S\ref{sec:timers}), applies or rejects the command with a
deterministic reason, allocates free seats in queue order and recomputes the next due time. The
worker then commits \emph{one}
\code{TransactWriteItems}~\cite{aws-ddb-transactions,aws-ddb-transactwriteitems}, including the
decision's notification rows (C4), with the META item conditioned on the snapshot's \code{version}
and incremented: an optimistic lock over the whole workshop behind the single writer (a conflict
reloads and decides again, at most three times). The command record is conditioned on being absent
or still ACCEPTED in the same transaction, so effects and settlement commit together, and a
redelivered or duplicated command fails the condition and is acknowledged without effect (C3). A
transaction holds at most 100 actions, so a decision is capped at 12 offers, 12 expiries and 90
items; the rest continues as an internal REALLOCATE command. A deterministic rejection settles the
command as REJECTED; an infrastructure error returns the message and the rest of its batch for
redelivery~\cite{aws-lambda-sqs-errors} after the 120\,s visibility timeout, and three failed
receives move it to an alarmed dead-letter queue (DLQ). TTL removes command records after 30 days
and notifications after 90; as in the Preliminary report it only tidies records and never times a
hold, because TTL deletion can lag by days~\cite{aws-ddb-ttl}.

\subsection{Rules R1--R7 and constraints C1--C7}\label{sec:rules}
Table~\ref{tab:rules} restates the rules and constraints in the Preliminary report's wording and
maps each to its enforcement. The Final refines four points. R2: the server accepts a request when
it enqueues it, so queue order is the FIFO enqueue order, recorded as the \code{seq} that the
workshop's single writer assigns. R4: the hold is configurable per workshop (\code{holdSeconds},
default 900\,s, minimum 30\,s; the expiry experiments use 60\,s). C5 is strengthened to tick
semantics in response to the TA's feedback (\S\ref{sec:timers}). The Preliminary report's
\enquote{a scheduled task performs the release} is replaced by one SQS delay timer per offer, with
the 5-minute sweep kept as a safety net (\S\ref{sec:timers}). Every rule and rejection reason has a
unit test, and a property-based test~\cite{claessen2000quickcheck,fastcheck} applies random command
sequences with random clock jumps and checks the invariants after every step (\S\ref{sec:results});
organisers can run the same check on a live workshop from the dashboard (\code{verify}).

\subsection{Responses to the TA's feedback}\label{sec:timers}
\paragraph{(1) Market size.} Added in \S\ref{sec:motivation} (Table~\ref{tab:market}).

\paragraph{(2) Per-offer timers instead of sweep-bounded expiry.}
In the Preliminary design a scheduled sweep released expired offers, so its interval bounded the
backfill latency. Each offer now has its own timer (Fig.~\ref{fig:seq}b). SQS FIFO queues do not
support per-message timers, and a message timer is at most 15 minutes~\cite{aws-sqs-timers}; the
worker therefore sends one TICK per new offer to a \emph{standard} delay queue with
$\text{DelaySeconds} = \min(900, \lceil \text{expiresAt} - \text{now} \rceil)$, \emph{before} its
commit (a timer whose commit fails finds nothing to expire). When due, the \code{expiryForwarder}
moves the TICK into the workshop's FIFO group (deduplication id \code{tick\#offerId\#expiresAt}), so
expiries take the same ordered single-writer path as user commands; a TICK that is still early
(holds over 15 minutes) returns to the delay queue. A TICK is only a wake-up call: every decision
begins by expiring all offers with $\text{expiresAt} \leq \text{now}$ (\emph{tick-first}). Hence late
or duplicate ticks are no-ops, an ACCEPT processed after \code{expiresAt} is rejected whether or not
its timer has arrived, and a late tick cannot touch a newer offer (the strengthened C5). The
5-minute sweep remains a safety net: each commit keeps the workshop's next due time on a sparse
index, and the sweep ticks every overdue workshop (lost timers, cut-offs, lost continuations);
\code{SweepLateExpiries} counts offers it expired more than 60\,s late (expected 0). The backfill
budget of an expiry is thus the delay-queue rounding (whole seconds), one forwarder invocation, one
FIFO enqueue and one worker decision; a decline or cancellation relays the seat inside its own
transaction. One-time EventBridge Scheduler schedules~\cite{aws-eventbridge-scheduler-types} would
lift the 15-minute limit but add a service, a schedule per offer and a role.

\paragraph{(3) How the browser learns that a 202 has settled: polling.}
The 202 response carries \code{href} and \code{pollAfterMs} = 300 (Fig.~\ref{fig:seq}a). The browser
polls \code{GET /commands/\{id\}} (strongly consistent) after 300, 500 and 1000\,ms, then every 2\,s,
and after 30\,s every 5\,s with a \enquote{still processing} note. The terminal state, APPLIED with a
result or REJECTED with a reason, carries the participant's registration summary (status, queue
position, offer expiry), so the interface updates from the poll alone and separates
\enquote{request received} from \enquote{seat confirmed}; a retry reuses the \code{commandId}. Changes
caused by others, such as a backfill offer, arrive through a 10\,s refresh while a registration is
QUEUED or OFFERED and the tab is visible. We did not use WebSockets: at pilot scale they add an API
type, a connection table and a failure path for little gain, while polling is bounded (about
\CostAssumeReadsPerCommand{} reads per command in the cost model). Server settle latency
(\code{settledAt} $-$ \code{acceptedAt}, \code{settledAt} taken just before the commit) is reported
separately from client-observed latency (Fig.~\ref{fig:seq}).

\subsection{Availability, security and privacy}
Every managed service is multi-AZ within the region, so an AZ failure needs no action; a worker
crash delays only its own workshop until redelivery (120\,s). A region failure is not covered: the
table could be restored from PITR, typically five minutes behind~\cite{aws-ddb-pitr-howitworks}, but
user identities live in one regional Cognito user pool without backup and the table's user ids are
Cognito subjects, so accounts would have to be recreated and remapped; this path is untested and we
claim no recovery time objective. The actor of every command comes only from the verified token, all
input is schema-validated, and organiser rights are checked in the API and again in the worker (C7).
Each function has its own role: the sweep only reads the table and the forwarder cannot access it,
while \code{api} and \code{worker} use SAM's table-level read-write template, which could be
narrowed. The API is throttled per stage and admits cross-origin requests only from the stage's
CloudFront and the local development origins; the experiment scripts' password sign-in client
is also an accepted audience, and both stages share one user pool. The application stores e-mail
address, display name and Cognito user id; access and function logs are kept for 14 days, raw
request events never. In the SES sandbox only verified addresses get
mail~\cite{aws-ses-production-access}, so pilot participants rely on in-app notifications.
